ECM Wiring Diagram

A Seeed XIAO ESP32C6 build standing in for the Wi-Fi module (WFM), wired to the fireplace controller's 8-pin Wi-Fi port. Five wires reach the port — power, ground, an enable line and two data lines — plus a sixth connection that ties the write-enable pin to the XIAO's own ground.

⚠️ This page documents the earlier Seeed XIAO ESP32C6 build. The current firmware targets an ESP32-S3 with a different pin map: RX GPIO14 ← ECM pin 6, TX GPIO21 → 1 kΩ → pin 4, write-enable sense GPIO1 → GND, 5 V pin 3 through the fuse, GND pin 8, and 1 kΩ from pin 1 to GND. GPIO2 is not used — it is the onboard IO2 LED. The current wiring table is in firmware/README.md, “Wiring”.

Status: bench-verified — the 0 V fault was the pin-1 gate

✅ The 0 V fault is RESOLVED — the gate is pin 1

The build came up dark at first — no LEDs, pin 3 at 0 V — because the ECM gates power to its Wi-Fi port on pin 1 being pulled LOW. Pin 1 is a module-presence line: a seated module holds it low; with the socket empty it floats high and the port stays dead.

Measured: pin 1 reads 0.06 V with the stock module fitted (pin 3 = 5.04 V) and 2.36 V with it removed (pin 3 = 0 V). ⭐ Confirmed by experiment: a 1 kΩ resistor from pin 1 to ground made the port power up and the ESP32 boot.

So the 0 V was not a fault — it is a gate doing its job. A dark device is not automatically a data-line wiring fault: check pin 1 first. And note this only applies when powering from pin 3; a USB-powered bench build neither needs the resistor nor is troubled by the gate.

⭐ The corrected record: the gate is pin 1, not pin 5.

⚠ The power plan's precondition was never met

Powering from pin 3 was always conditional on measuring the rail's current budget first — the stock module's TX peaked near 320 mA, an ESP32-C6 with Wi-Fi near 350 mA. No DC-current measurement of this port exists anywhere in the project.

The gate fault explains the 0 V, but the current budget remains unmeasured. Measure it before powering a build from this rail; it is an open item, not a closed one.

Connections

5 wires to the ECM — power, ground (pin 8), presence gate (pin 1) and two data lines — plus two 1 kΩ resistors: one in TX, one on the gate. D2 tied low = writes enabled, with no hardware interlock. ECM supplies the rail; share its ground.

What is verified, and what is not

⛔ Never USB and pin 3 together

On the XIAO the 5V pad and USB VBUS are the same node. Feeding pin 3's rail in while USB is plugged puts two sources on one net and backfeeds your laptop's port.

Bench: power from USB, leave pin 3 disconnected. In the appliance: pin 3 only, no USB — updates go over OTA.

⚠ Two different things are being called "pin 4 confirmed"

What is confirmed: the direction of the traffic on the channel the analyzer labelled D1 — module → ECM. That rests on content evidence (a new value appears on D1 0.176 s before the ECM announces it), not on a voltage reading.

What is not: that the channel labelled D1 is physically pin 4. That rests on one operator hookup record, of the same class as the disputed pin-3 reading, and it is entangled with the unresolved question of which end of the port each observer counted from.

docs/COMMAND_MAP.md states the first and reads as though it settled the second — that over-claim propagates into several other docs. Pin 6 has an independent anchor (post 296's two-point match); pin 4 has none.

One resistor on the TX line

1 kΩ in series, GPIO21 → pin 4, fitted at the XIAO end. Pin 4 is still unconfirmed: if it is an ECM output rather than its receive, GPIO21 is push-pull driving a driven line about 2.7 times a second, and the resistor bounds that to roughly 3 mA. At 9600 baud it costs nothing.

A 47 kΩ pull-up from the pin-4 node to the XIAO's 3V3 was considered and deferred. Without it the line is undriven while GPIO21 is high-Z — every reboot and every OTA. The ECM has been observed tolerating multi-second silences from an absent module, so this is a known trade rather than an oversight. If it is ever fitted, reference it to the XIAO's 3V3 and not to pin 5, whose rail-versus-input status is unresolved.

RX got no such resistor. It does not strictly need one — the far end is the ECM's confirmed TX idling at 3.2 V, in spec for a 3.3 V GPIO, so this is not a violated requirement. But the same argument made for TX applies by symmetry: a future misconfiguration, a stray boot glitch, or a pin-numbering error could put two push-pull drivers on one net with nothing to bound the current. Cheap insurance the install skipped.

⚠ Pin 3's current budget was never measured

The stock module's TX peaked around 320 mA; an ESP32-C6 with Wi-Fi peaks near 350 mA. This rail was to be checked before committing to it as the source — it never was, and no DC-current measurement of this port exists anywhere.

The fuse is drawn mid-span and neither end is specified — but which end you measure matters. 0 V at the XIAO pad with a live port means a blown fuse; 0 V at the port pin means the rail itself is dead. Separate the two before drawing any conclusion.

Powering from the ECM couples this device's failure domain to the ECM's — the accepted trade for reproducing the stock topology. The fuse and the bulk cap are what were meant to make that safe.

The analyzer rule still holds

Powering the device from pin 3 is a deliberate connection through a fuse. Clipping an instrument to pin 3 is still forbidden — it's a supply rail, not a signal, and probing it risks the analyzer while telling you nothing.

⚠ Writes are always enabled

D2 is tied to ground, so the firmware reads the write-enable input low and sends every command Home Assistant asks for. There is no hardware interlock — nothing physical can sever the TX line or stop a write.

What still holds: a reboot writes nothing, because intent starts unknown; and every write needs Home Assistant to explicitly ask first. To restore the gate, cut the D2–GND tie and insert a single-pole switch there — TX stays wired straight through.

A permanent tie to GND is safe here. On the ESP32-C6 the strapping pins are GPIO4, GPIO5, GPIO8, GPIO9, GPIO15 — GPIO2 is not one, so holding it low cannot disturb boot mode. (Worth having checked: a strapping pin tied to ground is exactly the kind of thing that "works" until one board revision doesn't.)

⚠ The build record is incomplete

The build uses pin-3 power, an inline fuse and the 1 kΩ TX resistor. Not recorded: whether the bulk cap is fitted (drawn above, marked ?), or the fuse's type and rating — "0.5–1 A" is a design band, not a measured part. The pin-1 gate resistor is what makes the port power up.

This is not bookkeeping. A blown fuse is one of the live hypotheses for the 0 V reading, and a fitted cap's inrush is a candidate trigger for another (a protective foldback). Both diagnoses depend on facts nobody wrote down.

Still open

The connector is unidentified — pitch unmeasured, part not matched. That is the gate on connecting any of this to the appliance.

Also not documented here: the XIAO's silkscreen-to-GPIO map this whole diagram rests on (D3=GPIO21, D4=GPIO22, D2=GPIO2). It checks out against Seeed's published pinout — but if it were wrong, RX and TX would be silently swapped at the pad level.

ECM owns ignition, flame sensing and the gas valve. This device is a control path, never a safety device. Port is powered only in IFT-REM — which is also the position where the fireplace can ignite.
