intellifire-esp32 ESPHome · ESP32-S3

Replacement Wi-Fi module for IntelliFire IFT 2.0

intellifire-esp32

The stock Wi-Fi module in this fireplace reboots roughly every 26 minutes. This project replaces it with an ESP32-S3 running ESPHome. The board sits on the ECM's 8-pin Wi-Fi port, answers the ECM's serial polls, and never initiates a frame. The only write path is a four-byte slot inside the reply to the 0x02BC poll.

01 · hardware

Wiring

The ECM exposes an 8-pin Wi-Fi port. Five pins are used: 1, 3, 4, 6 and 8. Pin 1 is a presence gate and must be pulled low through 1 kΩ to ground; without that strap the ECM never energises pin 3. Pin 3 is a fused 5 V rail (0.5–1 A, with bulk capacitance) and feeds the board's 5V pad. Pin 4 takes the ESP32's TX through a 1 kΩ series resistor. Pin 6 is the ECM's TX into GPIO14 and must never be driven. Pin 8 is the ground.

Pin 2 reads about 0 V but is not the return. Pin 5 is unresolved. Pin 7 is unconnected. On the board: RX GPIO14, TX GPIO21, write-enable sense GPIO1. The link is 9600 baud, 8-N-1, LSB first, 3.3 V logic on the ESP32 side.

  • Pin 6 is an ECM output. It is the ECM's transmit line and must never be driven.
  • Pin 2 is not ground. It reads ~0 V, but the return is pin 8.
  • Pin 5 is unresolved. Leave it unconnected until it has been measured.

02 · protocol

Exchange model

The ECM opens every exchange. It polls about 2.7 times a second — roughly every 0.764 s — with command 0x02BC, which asks for four bytes. The module replies with the same sequence number and the same command, carrying the four-byte slot. The ECM owns the counter; a reply that changes the sequence number is not a reply.

About 0.18 s after a slot command the ECM announces what changed. Every 1.11 s, on its own schedule, it sends the 0x00DC status frame. The next poll starts at least 158.6 ms after the previous frame ends, median 340 ms. A 12-byte reply drains in about 12.5 ms, leaving roughly 10× headroom.

Announcements are not acknowledgements

0xE4 (flame), 0xDF (pilot) and 0xE1 (height) fire about 0.18 s after a slot command, every time, even when the handler did nothing. The 0x00DC status frame is the only acknowledgement.

03 · write channel

Command slot

The 0x02BC poll asks for exactly four bytes. The payload is <opcode> 00 <value> 00; 00 00 00 00 is idle. Nothing else on the link changes appliance state, and the reconciler puts at most one slot in each reply.

0x64flame01 on · 00 offImplemented.
0x65pilot01 on · 00 offImplemented. Only bit 0 is effective.

Three opcodes in the emit path

The ECM has handlers for 0x66 and 0x68–0x6F, but the stock module never emits them and this firmware does not either. Only 0x64, 0x65 and 0x67 are reachable from Home Assistant.

04 · firmware

Reply pipeline

The reply path runs in a fixed order. The write-enable gate sits on the wire between the reconciler and the UART, not in Home Assistant. Telemetry taps both directions but publishes at the end of the loop iteration, after the reply has gone out.

03reconciler

All three desired values start as unknown, so a boot writes nothing. One write per poll, in fixed order: flame → pilot → height. Height is written only while flame is on. A failed write retries 2 s later; after four attempts in 8 s the firmware latches a command fault.

04write-enable gate

GPIO1 is re-read immediately before each write. Low is enabled, high is disabled. OFF commands are exempt and pass.

06telemetry

A bounded RAM ring holds both directions. The firmware keeps an opcode census and publishes it to MQTT under fireplace/ecm/…. Publishing runs at the end of the loop, after the reply is written, so it cannot delay the poll.

07home assistant

The ESPHome native API exposes the controls and state. Commands go into the reconciler; state and diagnostics come back through the same API.

05 · safety

Schedule IDs

0xC8–0xFF is 56 weekly-schedule IDs. Sending one programs a future actuator change. They are not control commands, and there is no reason to send one.

do not send

0xC8–0xFF

56 weekly-schedule IDs. The firmware will never send them.

  • Not observed from the stock module. The slot range extends beyond the implemented opcodes, but 0x66 and 0x68–0x6F stay out of the emit path here.
  • 0x68 can raise internal fault 6.
  • 0x69, 0x6B and 0x6C can reach the flame-level path.

06 · status frame

Status frame

0x00DC arrives about every 1.11 s: 31 bytes, 23 of them data. It is the only acknowledgement in the protocol, and it runs on its own cadence rather than answering a particular poll. These six capture indices are the ones the firmware maps.

Index 9 is the deadline flag

It was previously labelled “hot”. It isn't: the byte only reports that a 32-bit deadline is armed. Index 10 is the flame byte.

07 · build

Build and flash

ESPHome resolves the component through the external_components: block; a sibling components/ directory is not discovered automatically. The config expects firmware/secrets.yaml with ap_password, api_encryption_key, ota_password, mqtt_broker, mqtt_username and mqtt_password. There is deliberately no station Wi-Fi block: the device starts in AP mode and uses the captive portal to obtain credentials.

Validate the YAML before compiling. The host tests below run on a laptop against recorded captures and need no hardware.

cd firmware

esphome config fireplace-ecm.yaml    # validate schema, components and entity ids
esphome compile fireplace-ecm.yaml
esphome run fireplace-ecm.yaml --device /dev/cu.usbmodemXXXX
clang++ -std=c++20 -O1 -o /tmp/ecm_host_test test/ecm_host_test.cpp
/tmp/ecm_host_test ../captures      # protocol core + 6,145-frame replay
clang++ -std=c++20 -O1 -o /tmp/ecm_reconciler_test test/ecm_reconciler_test.cpp
/tmp/ecm_reconciler_test           # write-decision policy
  • Flash over the native USB-OTG port. The logger runs on USB_SERIAL_JTAG; the CH343 port needs an extra driver on macOS.
  • One module on the bus at a time. A second powered module collides on mDNS and MQTT, and two slaves would both answer on pin 4.
  • The C6 and the S3 do not share an image. The current target is the ESP32-S3. Never OTA a C6 build to it.

08 · limitations

Scope

ignition and gas
The ECM owns ignition, flame sensing and the gas valve. The ESP32 can request an action; it cannot bypass any of them.
pilot interlock
There is no pilot-before-flame interlock in the firmware, by design. That sequence lives in Home Assistant.
9-hour deadline
The deadline is extended only by slot-command activity. 0xBC polls do not extend it.
fault codes
The ECM's fault codes stay inside the ECM. The module can latch its own command fault; it cannot read the ECM's.

This project changes how the appliance is asked. It does not change what the ECM will allow.
